# 高效完整构建合同

性能优化不得省略来源、选层、分析深度、证据、公式核验或原定检索问题。用户接受10篇常规论文约30分钟作为效率参考，要求优化构建流程本身。衡量真实冷构建和复用耗时，按内容与验收结果完成；不设置总限时、阶段时间配额或倒计时，也不为达成某个分钟数删减分析。

一次阅读冻结 context、result-template、技能与完整 prepared_sources；必要时查看原 PDF 图和公式。先规划语义主题，再写单一 canonical analysis，避免反复探索同一工具、打印相同长原文、重复输出同一知识正文。

引文默认选支持该判断的完整短段，通常100–600字符；不是硬截断。公式连同定义、实验条件和脚注需要更长时保留。原文双索引已保存整页/函数上下文，不为每条主张反复生成整页文本。evidence_catalog 一次登记，所有主张和题目只写ID。卡片按机制合并，不机械要求每篇每层各造一张；30–50道题仍完整保留并批量执行。

知序 v4 使用 output_dir/knowledge-analysis.json，包含 knowledge_cards、knowledge_build_report、knowledge_relations 和 warnings。卡片/证据结构遵循原交接合同，全部正文、来源分析、层覆盖、全部验收问题保留。运行 `python app/scripts/knowledge_finalize.py <context.json> <knowledge-analysis.json>` 生成分层 Markdown、覆盖报告、哈希和 result.json；该工具只渲染已有分析，不替代理解或校验。

术语与别名来自正文概念及合法同义词，提供紧凑中英语义线索，不把验收问题原句写成搜索别名。索引所有正文，语义模型分块在模型令牌范围内；不能把未入向量的尾文称为完整语义召回。

复用必须匹配每个冻结来源 SHA、完整选层与侧重点，并核验全部产物哈希及引文版本。模型文件版本、分词器、查询指令、切块与分词规则、知识内容哈希共同控制向量复用。复用已发布分析、失败后的完整分析检查点、全文预处理缓存和冷构建分别记录；不拿暖缓存冒充从零构建。

检索失败先保留完整分析与失败题诊断，重新构建索引并跑全部原题；除非内容/来源不合格，不重新生成整套分析。不得移除失败题、替换预期卡片或降低门槛。完整分析被复用时仍需全部证据/索引验收。

记录实际提交、预处理、分析开始/结束、验证、发布和首次可交互时间；日志缺失时说明无法精确拆分，不能推算后伪装实测。50/100/200 篇用真实不同资料和各阶段统计验证；重复同一论文或模拟节点只能验证界面负载，不能证明大规模深度理解耗时。

原知识库和资料只读。所有登记/发布通过公开 API/kw；自动任务定稿后退出，由平台负责 ingest/assemble。

减少重复输出：analysis 可用 evidence_catalog 为每段原文登记一次，卡片/主张/验收题引用ID；方法卡省略的未知字段由定稿工具明确补为 null/unknown。结果仍展开全部证据并通过原有验收。检索发布失败导致事务回滚时，重试从同一任务保存的 result.json（公共重试已归档时读取 result.previous.json）恢复分析，重新核对所有产物哈希、来源、版本和题集，不重新让模型抄写全文。完整检查点只能保守调整整卡标签及失败记录格式，不能改写原主张或证据；保留一份原清单。

长资料分批整理时，每完成一组方法或实验卡就覆盖保存同一 knowledge-analysis.json 检查点，并在 stage-result.json 更新阶段、已完成卡片数与最后更新时间；不要只把全部草稿留在会话内存中，也不要为每批复制整目录。未齐全的分析仍是草稿。恢复时先核验冻结来源和已写证据，再补尚缺的内容与题目；完整清单仍只在全部完成后生成。
